# Pi Remote Control — design

## Goal

Join **already-running interactive Pi processes**, including halfway through a conversation. One self-hosted server shows all connected sessions and lets a phone read the current branch, send a message, and stop a run. The server does not start another Pi process or edit session files.

## Shape

```text
Pi TUI + extension ── outbound authenticated WebSocket ── server ── authenticated web UI
Pi TUI + extension ── outbound authenticated WebSocket ──┘          (mobile/PWA)
```

- Each extension instance owns one live Pi process. Loading the extension registers `/rc` but does not connect; `/rc` opts the current session in, even mid-conversation, and `/rc close` disconnects and stops retries. An active instance reconnects on network failure; a Pi session replacement/shutdown disconnects, so opt in again with `/rc` in the new session.
- The extension reads `ctx.sessionManager.getBranch()` for the complete **active branch**, including messages written before the extension connected and before compaction. It sends a fresh snapshot on connection, request, and `session_tree` navigation. Other branches are out of scope.
- It forwards message/agent lifecycle events for live output and accepts `prompt` and `abort` commands for its *current* session only. Use `pi.sendUserMessage()` and `ctx.abort()`; a browser prompt that arrives while Pi is busy waits in the extension (extensions cannot edit Pi's own queue), and later ones join it. In `agent_before_settle`, which Pi awaits while the run is still active, the extension sends them to Pi as one `followUp` joined by blank lines and waits until `hasPendingMessages()`, so Pi continues the same run as it does for its own follow-ups. Pi skips that event after a Stop, so a queue still waiting at `agent_settled` means either the run was stopped (a browser `abort`, or the run's abort signal for a terminal Esc), in which case the text goes back into Pi's editor as Pi does with its own queue, or the prompt arrived after `agent_before_settle`, in which case it is sent then (Pi defers prompts sent during `agent_settled`). A prompt while Pi is idle is sent at once, together with anything still waiting, and a manual `/compact` (not an agent run) delivers the queue on the next tick after `session_compact`. Every send uses `followUp`, which Pi ignores when idle. The list survives `/rc close`. Limits: Pi drains its own queue before `agent_before_settle`, so a terminal follow-up sent after a waiting browser prompt runs first; and a Pi `input` handler still processing the hand-off can submit it after a Stop, as with any extension prompt. Never mutate JSONL directly.
- Background work comes from other extensions' in-process `pi.events` protocols, so neither is a dependency and each part stays empty when its extension is not loaded. Shells: on `processes:changed` the extension emits `processes:request:list` with a `reply` callback that pi-processes calls synchronously, and keeps rows whose status is `running`, `terminating`, or `terminate_timeout` (that protocol is internal to pi-processes, so every field is validated). Subagents: on pi-subagents' `subagents:rpc:v1:ready`, `subagent:async-started`, `subagent:async-complete`, `subagent:child-status`, and `subagent:foreground-complete` it sends one RPC `status` request at a time and reads the documented `data.fleet` v1 entries from the reply channel, giving up after 5 s without a reply. Both refresh on every `hello`, and an update is sent only when the list changed.
- The server routes commands by authenticated connection + session ID, holds connected-session metadata in memory, and relays snapshots/events to browser clients. An agent disconnect marks it offline. The server stores each process's metadata and latest complete snapshot (chunked snapshots as raw JSON string literals) in a private state dir, `$XDG_STATE_HOME/prc` or `~/.local/state/prc` (0700 dir, 0600 files, atomic writes, file names from sha256(processId)); it loads stored sessions as offline at startup, keeps the 50 most recent, and drops an offline entry when its session ID reconnects from a new process. Stop `prc` and delete the dir to clear it. Browser reconnect requests a fresh snapshot, not an unreliable event replay. Each Pi session gets its own entry, so `/new` or `/resume` followed by `/rc` adds a row instead of replacing the previous conversation; commands still require the matching session ID.
- Use a Rust `prc` executable with a small HTTP/WebSocket stack, JSON messages, and the **built React + Vite app embedded into the binary**. The Pi extension remains a separately installed TypeScript/npm package. React runs entirely in the browser; no SSR or Node runtime on the server host.
- The mobile-first UI has a session list (name, folder and git branch, busy/offline, recency; a per-session ⋯ menu to show session info (machine hostname, full path, branch, session ID, each copyable), rename (clicking the conversation title also renames it in place), pin to the top in this browser, or remove offline entries), complete active-branch history, streaming response, composer with a combined model/effort menu, rename, and stop. Text/tool output is escaped as text, never inserted as HTML. Terminal-only custom dialogs are not remotely controllable in v1.

## Wire contract (v1)

JSON WebSocket messages. Agent connection: `/agent`, `Authorization: Bearer <agent token>`. Browser connection: `/ui`, authenticated cookie plus exact Origin match. `processId` is a random entry ID assigned per Pi session within a Pi process (reused across `/reload` of that session); `sessionId` comes from Pi and must match before any command executes.

- Agent → server: `hello {processId,sessionId,name,cwd,host?,branch?,busy,waiting?,asking?,updatedAt?,model?,thinkingLevel?,context?,queued?,background?,models?}` (`context` is `{tokens,contextWindow}` from Pi's `getContextUsage()`, `tokens` null while unknown; `message_end` and `agent_settled` events carry a fresh one as `contextUsage`, which the server keeps and persists as session `context`; the UI shows it with cost summed from snapshot `usage`; `queued` lists one-line previews of up to 20 browser prompts waiting in the extension, updated by a `queue_update {queued}` event, kept in memory only and cleared when the agent disconnects; `background` lists up to 20 display-only `{kind: shell|agent, id, label, detail, full?, startedAt}` items (`detail` is a one-line preview of at most 200 characters; `full`, at most 1000, is sent only when `detail` was shortened and appears when the item is tapped; a separate field because older servers drop a `detail` over 256) for work other extensions report as running, updated by a `background_update {background}` event and kept and cleared the same way), `snapshot {processId,sessionId,entries}` or ordered `snapshot_chunk {processId,sessionId,snapshotId,index,total,data}` for large histories, `event {processId,sessionId,event}`, `models {processId,sessionId,models}` (reply to server `models {sessionId}`, computed live like hello `models`). `entries` are the ordered active-branch session entries, not model-compacted context. `data` chunks reassemble into the JSON-encoded entries; chunk frames stay below transport limits.
- Server → agent: `history {sessionId}`, `prompt {sessionId,text}`, `abort {sessionId}`, `models {sessionId}`, `set_model {sessionId,provider,modelId}`, `set_thinking {sessionId,level}`, `rename {sessionId,name}`.
- Browser → server: `select {processId}`, `remove {processId}` (offline sessions only; deletes the stored copy), `prompt {processId,sessionId,text}`, `abort {processId,sessionId}`, `models {processId}`, `set_model {processId,sessionId,provider,modelId}`, `set_thinking {processId,sessionId,level}`, `rename {processId,sessionId,name}`.
- Server → browser: `sessions {sessions:[{processId,sessionId,connectionId,name,cwd,host,branch,busy,busySince,waiting,online,updatedAt,model,thinkingLevel}],now}` (`busySince` is the server time of the run's latest `agent_start`, kept across hellos and agent reconnects for the same session, null when idle; `now` is the server time when the frame was sent, so the browser corrects `busySince` for its own clock; the UI shows "Thinking (Ns)" above the composer, or "Running (Ns)" while a finished assistant turn has a tool call without a result, like the Pi terminal status line), `models {processId,sessionId,models}` (the cached list to the requesting browser; an agent refresh to all browsers), `snapshot {processId,sessionId,entries}` (or relayed `snapshot_chunk`), `event {processId,sessionId,event}`, `error {message}`. `connectionId` is a server-assigned socket identity that changes when an agent socket is replaced, even if the Pi session ID does not. An `event` contains only the Pi event types needed for display: message start/update/end, agent start/settled, and `ui_prompt_start`/`ui_prompt_end` (Pi is blocked on an extension dialog; the server keeps an in-memory `waiting` flag and the UI shows "Needs input", but the dialog is answered in the terminal). The extension adds `summary` (at most 160 characters: the final reply's closing question, else its opening paragraph) and `asking` (that closing paragraph ends with `?`) to `agent_settled`; `asking` also shows "Needs input" until the next `agent_start`; after finalized messages the extension/server refreshes the snapshot so the UI cannot duplicate a streamed message. Disconnected processes remain listed with `online:false`, including after server restart, but cannot receive commands; `select` on one replays only its stored snapshot for its current session ID (same `snapshot`/`snapshot_chunk` shapes, fresh `snapshotId`), or nothing if none is stored.

Model control: hello `model` is `{provider,id,name,reasoning,thinkingLevels}` or null (levels mirror Pi's supported levels for that model), `thinkingLevel` is one of `off|minimal|low|medium|high|xhigh|max`, and `models` is `[{provider,id,name,reasoning}]` from Pi's scoped models, or all auth-configured models when unscoped, deduplicated by provider/id. The server ignores (treats as absent) any invalid or oversized optional hello field without closing the socket: at most 2000 models (invalid entries are dropped individually), strings at most 256 UTF-16 units, levels only from the enum. It persists `model` and `thinkingLevel` with session metadata (optional, so older metadata still loads) and keeps `models` in memory only. Pi has no catalog-changed event, so a browser `models` request (sent on select and whenever the model menu opens) also forwards `models {sessionId}` to the agent, whose reply (same bounds as hello) replaces the stored list and is broadcast; `models` for an offline or unknown process gets no reply. `set_model` and `set_thinking` need an online process (otherwise `Process is offline`); the commands also need the current session ID, `set_model` a provider/model pair from that session's advertised list, and `set_thinking` an enum level (otherwise `Invalid or stale command`). The extension re-checks the model against its advertised list, calls `pi.setModel()` (warning in the terminal if Pi refuses) or `pi.setThinkingLevel()` (Pi clamps to the model), and sends a fresh `hello` on `model_select` and `thinking_level_select`. `rename` likewise needs an online process, the current session ID, and a string `name` of at most 1024 UTF-16 units; the extension calls `pi.setSessionName(name.trim())` (empty clears the name, so the title falls back to the first prompt), and Pi's `session_info_changed` triggers the fresh `hello`. The server never renames offline sessions.

Reject oversized, invalid, or stale commands; do not trust browser-supplied session identity. A protocol/frame error closes only its socket, not the server. Snapshots and updates may race: the latest complete snapshot replaces rendered finalized history, while the currently streaming assistant text stays ephemeral. Discard ephemeral stream state on browser disconnect before requesting fresh history.

## Security and deployment

- `prc serve` binds `127.0.0.1` by default, behind private HTTPS via Tailscale Serve (not Funnel). The canonical `publicOrigin` is its exact `https://<tailnet-host>` origin (no path/trailing slash); browser Origin checks also allow exact loopback origins on that port only for a loopback bind. `RC_PUBLIC_ORIGIN` overrides the canonical origin for the server only. The Pi extension uses the origin in its private config to derive `wss://.../agent` unless paired `PI_RC_*` overrides or private client config apply. Keep other existing `RC_*` environment overrides as escape hatches, but ordinary users should need only the private config.
- Agents authenticate with a separate high-entropy shared token; browser users sign in with an admin password and receive an HttpOnly, SameSite cookie. Check the Origin on browser WebSocket upgrades and state-changing requests. No credentials in URL/query strings, logs, or browser storage.
- Remote users can cause Pi to run tools with local OS permissions. Treat access like SSH: one trusted user, no public anonymous endpoints, and never put transcripts or secrets in push payloads.

## Browser notifications

- Provide an installable PWA with a service worker and opt-in Web Push for `agent_settled` (body: its `summary`, else "Finished responding") and `ui_prompt_start` (body "Needs your input" plus the dialog title, at most 120 characters) over HTTPS; the title is the session name. VAPID keys come from paired `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` or are generated once into `<state_dir>/vapid.json` (0600); subscriptions persist in `<state_dir>/subscriptions.json` (0600, at most 100). The encrypted payload carries only the session name (title, which may be the first prompt), "Finished responding", and process/session IDs; clicking opens that session. On plain-HTTP localhost the UI falls back to in-page notifications while the tab is open. On iPhone, background notifications require adding the web app to the Home Screen and granting permission. Core control must work when push is unsupported.

## Setup and service lifecycle

Like tinyllm, keep durable credentials in a private config file rather than shell exports or a readable service definition. `prc setup` creates `~/.config/prc/config.json` (or `$XDG_CONFIG_HOME/prc/config.json`) with mode 0600, generates an agent token and admin password, prints the one-time admin password and exact browser URL, and never overwrites an existing config. `prc serve` loads that file; existing `RC_*` environment variables remain explicit overrides. A missing config and missing credentials fail with a clear setup instruction.

A legacy `config.json` or `client.json` in the old default directory blocks setup and default config reads when the new config is absent; users manually move both files to the new default without overwriting, retain mode 0600, then restart the server and reload/reconnect Pi. Explicit `RC_CONFIG` bypasses this migration guard.

The Pi package is npm-installable and contains only `extensions/remote-control.ts` plus its `ws` runtime dependency; Node 22.18+ is required on the Pi host, not the server host. `/rc` reads the same private config on the server host and derives the agent WebSocket URL from its public origin; `PI_RC_URL` and `PI_RC_AGENT_TOKEN` remain paired overrides for Pi processes on other machines. `/rc setup` shows the effective connection setup with the token redacted and can change the client URL in a separate mode-0600 `client.json`; token changes require editing that private file outside Pi because its normal input dialog does not mask text. The login UI distinguishes wrong password (401) from a disallowed address (403); restart the currently running server after changing its config.

Ship example **macOS LaunchAgent plist** and **Linux systemd user unit** that invoke an absolute `prc serve` binary path from a stable install directory. The private config stays out of unit files. Document installing/enabling, status/logs, restart after updates, and the fact that LaunchAgent starts at login, while systemd lingering is opt-in for boot startup after logout. No Node toolchain or repository checkout is required on end-user server hosts.

Release build: version-tag CI installs frontend dependencies from `server/web/`, builds React/Vite to `server/web/dist`, embeds that directory when compiling `prc` for macOS arm64/amd64 and Linux (glibc) amd64/arm64 with static curl, OpenSSL, and zlib, and publishes per-platform `.tar.gz` archives plus `checksums.txt`, a multi-arch distroless GHCR image, and the `@mipsel64/pi-remote-control` npm extension. `prc` must serve `index.html`, hashed static assets, icons, manifest, and service worker from the embedded bytes with correct content types and cache policies. Never read frontend assets from a checkout at runtime. Keep the existing `/agent` and `/ui` wire protocol and `/api` auth/push behavior stable so the Pi extension does not need a second protocol migration.

## Acceptance

1. Start two ordinary interactive Pi processes with the extension loaded; both appear independently in the browser.
2. Connect an extension after Pi already has history; the web UI shows the complete active-branch conversation before a new message is sent.
3. Send a prompt from the browser, see live output, and abort or queue a follow-up while busy. Reconnect the browser/agent without losing the current history while Pi stays running.
4. Browser/agent without credentials cannot read history or control sessions. Loading an extension without `/rc` does not open a socket.
5. Rust tests exercise authentication, routing/session ownership, reconnect/history, and optional push; a frontend build/check covers client rendering behavior. A release binary serves embedded assets when run outside the repo with no Node installation.
